Oktavia DC The data center fabric and the services of every application, declared once and verified on every Nexus

For data center teams and colocation providers: Oktavia builds and operates the Cisco Nexus VXLAN EVPN fabric —underlay, BGP EVPN, VTEP and vPC— and orchestrates what each application needs: its VRF, its server networks with anycast gateway, its ports and its exit to the outside. Every change reaches all the Nexus switches as a single transaction with a checkpoint, and it is not accepted until the fabric has converged.

Request a demo See the services
  • Per-service intent, not per device. VRF, network, port or external exit; Oktavia knows which leafs, border and spines get each line.
  • Checkpoint transaction. A checkpoint on every Nexus, config, then OSPF, EVPN and vPC verification; if anything fails, all of them roll back on their own.
  • Model-driven. NX-API (JSON-RPC) with certificate fingerprint pinning, no screen scraping.
  • Only what is missing. The plan is compared with the running config and sends only the new lines; on confirmation it is saved to the startup config.

What it solves

Provisioning an application should not mean editing every Nexus by hand.

A new network in a fabric touches the VLAN, the VNI, the anycast SVI, EVPN and NVE on every leaf, the VRF on every VTEP and the server port on the vPC pair. Oktavia turns that work into one declaration and one reviewed change.

keyboard

The same config on every leaf

The service is declared once and Oktavia generates each leaf, border and spine part from that same declaration: VLAN, VNI, anycast gateway, VRF with its L3VNI and automatic RD/RT.

A half-applied change breaks the fabric

A checkpoint on every Nexus before touching anything; if one device rejects a line or the fabric does not converge, all of them return to the checkpoint. The change only stays when a person confirms it.

Drift nobody sees

Every service is compared with the running config block by block, and state tests check OSPF, EVPN sessions, VNIs up and the vPC pair with its keepalive.

Where does the traffic go?

Per-VRF routes on every Nexus, the VXLAN hop to the remote VTEP and the exit through the border: routing analysis and topology follow an application's real path.

How it works

From service intent to audit, in a single cycle.

01

Per-service intent

Declare the VRF, network, port or external exit (with a form, a workflow or Argos). Oktavia distributes it to the Nexus switches involved.

02

Transaction in the Digital Twin

One change for the whole fabric: a dry run on every Nexus, a checkpoint, only the missing lines and OSPF, EVPN, vPC and VNI verification.

03

Human confirmation

A window to confirm; on confirmation the config is saved to the startup config. Without it, the fabric rolls back to the checkpoint on its own.

04

Audit

Per-service compliance compares the intent with the running config again, and the fabric state confirms the application is still up.

Server network

VLAN, VNI with BGP ingress replication and an anycast gateway: the same IP and MAC on every leaf.

Server port

Single access or vPC with LACP on the leaf pair, as a spanning-tree edge.

public

External exit

The border interface in the VRF and eBGP with the WAN router: the default route enters the fabric and the application's networks go out.

Visibility

Every service with its components, its values and its real state.

The orchestrated services table shows every VRF, network, port and exit with all its values, and its path on every Nexus: declared versus seen. The page of a composite service breaks it down into components (underlay, BGP, VTEP, vPC…) with their per-device parameters and what is missing according to the last audit.
