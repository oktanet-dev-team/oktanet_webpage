1. Executive summary

Oktavia is a network automation platform for enterprise IT operations. It pairs an automation engine with a unified web interface to run audits, verify configuration compliance, visualize network state, and manage changes in a controlled and traceable way.

It is built for teams that need to move fast without giving up control. Every action produces versioned artifacts, every change requires prior validation, and everything lands in a searchable history.

What sets Oktavia apart: true multi-vendor in production across Cisco IOS and IOS-XE, Fortinet FortiGate and FortiSwitch, and Juniper Junos; Argos as a ChatOps layer across the whole platform; network security with configuration evidence; service inventory; and the full detect, remediate, and verify cycle on all four vendors.

2. The problem it solves

Enterprise networks grow more complex faster than the teams that run them. The symptoms repeat across almost every customer:

  • Manual audits that take days and depend on nobody misreading a configuration.
  • Configuration drift that goes unnoticed until there is an incident.
  • Fragmented visibility across inventory, compliance, topology, and metrics, each in its own tool.
  • No traceability on who changed what, when, and with whose approval.
  • Reactive operations: the team acts when a user reports, not when the network drifts.
  • Diagnosis without closure: audit tools find the problem, but fixing it stays manual work outside the tool.

6. The closed loop

This is what separates Oktavia from an audit tool. Finding a problem is worthless if fixing it stays manual, and applying a change blind is worthless if nobody verifies it landed right. The loop is a single path walked without leaving the platform:

  1. Audit the chosen scope: a device, a role, a site, or the whole network.
  2. Read the compliance result: what failed, at what severity, and which configuration lines are missing.
  3. Propose the change against declared intent, not against a generic template.
  4. Review the diff between desired and live configuration in the Digital Twin, with estimated impact.
  5. Approve. A person, always. No change applies on its own.
  6. Apply using each vendor safe primitive.
  7. Verify: audit again and confirm the finding closed.

Every step leaves a downloadable artifact and lands in the job history. If the result is not convincing, there is a way back.

How it applies on each vendor

VendorApply primitiveSafety net
Juniper JunosDeferred commit confirmation over NETCONFThe device rolls back on its own if nobody confirms within the window. A session that drops mid-apply does not leave the device unreachable.
Fortinet FortiGateOperations over the configuration APIChanges touching administrators and zones stay in permanent simulation, because moving a zone invalidates the policies referencing it.
Fortinet FortiSwitch · Cisco IOSSecure session with vault credentialsDiff before and verification after. The rollback is the inverse change, also reviewed and approved.

7. New service rollout

The same cycle rolls out services, not just corrects deviations. You describe what you want and Oktavia proposes it as declared intent:

  • A tunnel between two sites, with the routes that run through it, and its complete teardown when the project ends.
  • Advertising a network: logical interface, OSPF announcement, access control lists, and BGP on the site edge devices, with ping verification.
  • Editing routing: router identifier from the logical interface, recommended site summarization.
  • DHCP for a VLAN, with the range proposed from what Oktavia already knows about the segment.
  • Adopting what exists: read a device backup and declare as intent what it already has configured, so auditing can start without redesigning anything.

Every service is proposed, edited before applying, and ships with its rollback. Nothing is written to the network without a person approving it.

8. Argos, the network ChatOps

Argos is the assistant embedded in every Oktavia screen. You ask in plain language and it answers with network data, not generalities. It covers four moments of daily work:

  • Understand: network state, compliance, what to address first, diagnosis of a device or a site.
  • Investigate: path between two IP addresses forward and back, correlation of failures against configuration, anomaly and unreachable device detection.
  • Configure: describe the service in plain language or paste the configuration, and Argos proposes it as declared intent for the operator to edit before applying.
  • Close the loop: audit, read compliance, take it to the Digital Twin, approve, and verify. Each step is a button, not a sentence you have to type.

Two design principles separate it from a generic assistant. Every answer states whether it consumed the language model or resolved deterministically, so the cost is visible before you click. And no action that touches the network happens without a person approving it.

What uses AI and what does not

Most of what Argos does never touches the model: they are queries and calculations over already collected data, with reproducible results. The model steps in when something has to be written, prioritized, or interpreted from free text.

9. Security and service inventory

Network security

Security posture computed on the collected configuration of firewalls and switches, across four domains: perimeter, management plane, identities, and segmentation. Each finding carries the configuration line backing it and its recommendation in the vendor own syntax. It includes a global and per-device score, and filters by domain and severity.

Service inventory

It answers the question that comes before compliance: what is configured on each device, and how much of it is declared as intent. It cross-checks what is observed against what is declared and against the service catalog, and classifies each service into four states, along with the configuration scope that defines it.

StateMeaning
CoveredThe service is configured on the device and declared as intent. Oktavia audits it.
Blind spotIt is configured on the device but nobody declared it. Nobody audits it, and a change to it goes unnoticed.
Not appliedIt is declared as intent but does not appear in the device configuration.
Not applicableIt does not correspond to the platform or the role of that device.

From the inventory itself, blind spots are declared as intent in a single step, without touching the network: what was already there simply starts being audited.

12. Architecture and operating model

The platform separates the web interface from the automation engine. The interface owns the user experience, tenant organization, and persistence; the engine executes against the devices. They talk over a REST API authenticated with a key.

  • Persistence: relational database with per-tenant data separation.
  • Artifacts: JSON, CSV, and configuration files, downloadable and versioned.
  • Deployment: orchestrated containers, on customer premises or in a private cloud.
  • Device access: SSH, NETCONF, and native vendor API, with credentials encrypted in a vault.

Operating model

  • Everything runs as asynchronous jobs with complete history.
  • Every job produces versioned artifacts, downloadable.
  • No direct changes are ever applied without generating and validating artifacts first.
  • Remediation actions are supervised and traceable, with an identified approver.

13. Platform security

Oktavia has read access and, when the customer authorizes it, change access to their network. Its own security is part of the scope, not an annex.

Where the data lives

The platform is deployed on the customer infrastructure, on premises or in their private cloud. Inventory, configurations, and artifacts do not leave it. The only exception is AI analysis: when an action that consumes the model runs, the content that query needs travels to the AI provider. Argos states before every action whether it will consume it, so the decision is the operator's, case by case, and the deterministic capabilities cover most of the work without sending anything.

Device credentials

They are stored encrypted at rest in the database, with a key that lives in the deployment configuration and not in the code. They are never shown in the interface nor written to logs. We recommend read-only credentials for discovery, and separate change credentials only if remediation is in scope.

Access to the platform

Mandatory login, integrated with the corporate identity provider. On top of that, an access allowlist by IP address or network, managed from the interface itself, with two modes: monitor, which logs rejections without blocking, and strict, which blocks. Switching to strict is guarded: it cannot be enabled if the operator own address is not covered. The same list applies to the web interface and to the automation engine.

Data separation

Multi-tenant with row-level separation: every query is scoped to the user organization. One customer data is not reachable from another customer session, not even through a programming mistake.

Between components

The web interface and the automation engine authenticate with a key on every call, in both directions. The engine exposes no operation without it.

No change without approval

This is a security property too, not only a process one: no action that writes to the network happens without a person approving it, and every application is recorded with its approver, its diff, and its artifact.

Corporate identity and second factor

Login integrates with the customer identity provider over OpenID Connect. Oktavia supports Okta, and with it single sign-on and whatever second factor the provider policy already enforces: onboarding, offboarding, and passwords live where the corporate directory already lives, with no parallel user list to maintain. Local passwords are kept for contingency only.

The platform can also require the authentication to be recent, not merely that a session exists at the provider: it can demand a fresh authentication event, restrict the accepted methods, a passkey for example, and require a specific assurance level, such as the Okta two-factor one. That is what makes closing the browser ask for the second factor again.

Confidentiality. Handling of customer information is governed by the confidentiality agreement signed at the start of the project, with the scope, retention, and return or destruction of the data agreed there.

14. Integration requirements

To deploy Oktavia over an existing network we ask the customer for:

  • Base device inventory.
  • List of sites and site types.
  • Operational roles per device.
  • Vendor, platform, and version, where the data exists.
  • Management addresses and access method.
  • Read credentials for discovery.
  • Change credentials, if remediation is in scope.
  • Backups or available live configuration.
  • Current configuration standards.
  • Operational constraints and change windows.
  • Approvers and technical contacts.

Minimum data per device

Identity (hostname, management address, site, role), operating system and model, interfaces, layer 2 discovery neighbors, BGP and OSPF neighbors where they exist, live configuration or backup, and the baseline operational services: NTP, DNS, SNMP, SSH, banners, and time zone.

Preferred order for sourcing the data

  1. Native vendor API.
  2. NETCONF, RESTCONF, or remote procedure calls.
  3. Structured vendor parsers.
  4. Command-line output parsing.
  5. Live configuration or backups.

15. Implementation process

  1. Data onboarding. Receive the base inventory, normalize names, roles, sites, platforms, and models, and load the initial file.
  2. Controlled discovery. Validate reachability, run discovery in batches, collect backups, and normalize the observed inventory.
  3. Intent baseline. Define services per scope, load service variables, enable compliance checks, and configure the customer service catalog.
  4. Validation. Run the full audit, review the dashboards, and tune rules and exceptions.
  5. Operation and remediation. Propose the change, simulate it, approve it, apply it, and recompute compliance to confirm closure.

AI accelerates the preparation: inventory cleanup, role and platform normalization, parser prototyping, and catalog generation. Final validation of intent, compliance, and changes stays operational and human.

The complete platform is Oktavia Pro. Continuous telemetry and event orchestration are licensed separately because they have a different consumption profile, they store time series and run a permanent evaluator, and not every network needs them on day one.
