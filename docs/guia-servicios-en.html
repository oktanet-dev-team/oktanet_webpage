Guide for network engineers

Services and templates: view, test and extend without development

How to see what each service generates on your devices, test a change before saving it, and add what the template doesn't include. You work with parameters; Oktavia takes care of the template, the gate and the tests.

1. Who this guide is for

For network and automation engineers, at customers or partners, who maintain a network's services in Oktavia: Campus, WAN, Security and Management in an enterprise; Transport, Services, Security and Management at a provider.

By the end you will be able to read a service end to end, test a value against a real device without saving anything, and add to a service what its template doesn't include, without writing Jinja and without asking for development.

This guide complements the Intent guide, which explains scopes and the change cycle. If this is your first time with Oktavia, start there.

2. The idea: parameters, not Jinja

Every Oktavia service has a tested base template that turns values into configuration. That template is not edited: it is extended. That way an Oktavia update doesn't overwrite your work, and your work doesn't break the template.

Your work as an engineer is in the parameters: which values, in which scope and with which network test. An extension's template comes from the Oktavia catalog or is proposed by Argos, and a deterministic gate decides whether it can be published.

PieceWho makes itWhere it lives
Base templateOktavia.The service catalog. Not touched.
ExtensionThe Oktavia catalog, with one click, or Argos from your description.Next to the service it extends.
ValuesYou.The intent (service_vars), in the scope you choose.
TestsOktavia derives them from the template and the parameters.The compliance of every audit.

Saving values does not touch the network. They reach the devices through the usual cycle: audit, compliance, Digital Twin, you approve, and verification confirms it.

3. Your domain's services

Open Services and pick the domain. The tab formerly called Intent is now called Services: it lists every service in the domain, declared or not.

ColumnWhat it says
PlatformWhich systems the service exists for: ios, iosxe, xr…
Declared inThe scopes where it has values.
DevicesHow many devices it applies to.
Failures and %Its compliance in the last audit.
TestsHow many config and state tests validate it; "no tests" if none.

Undeclared services come last, with a link to declare them. The domain Summary also shows each service's platform.

4. The service page

Each service in the list opens its own page. It gathers in one place everything you need to understand and change it:

  1. Declared values: every scope where it is declared, with its values, and the buttons to edit them, view the template and extend (section 5).
  2. Test with a device: values, template and result, side by side, for a real device (section 6).
  3. ✦ Explain this service: Argos explains what it does and what it generates (section 7).
  4. ＋ Extend this service and Advanced options: what you can add to it (section 9).
  5. Devices where it is active, by site, with ⚠ on the failing ones, and Tests that validate it.

Tests come in two kinds. Config tests compare the running configuration with what the template generates, one rule per device. State tests check that the service works on the network.

5. Declared values and "See what changes"

The Declared values fold shows every scope where the service lives —defaults, by_role, by_site, by_device, by_model, by_platform…— with its values. Edit values, Template and Extend here sit on the same row.

Edit and see what changes

  1. Click Edit values on the scope you want to change. A JSON editor opens.
  2. Change the values.
  3. Click See what changes. Oktavia shows, per device, the lines of the desired configuration that would change: − what is there today, + what your change leaves. Secrets stay hidden.
  4. If it is what you expected, click Save. If not, adjust and look again.
r1
  router bgp 65001
+  neighbor 198.51.100.1 timers 10 30

These are real configuration lines, not just values. If a device you didn't expect shows up in the list, your scope is wider than you thought: don't save yet.

What you need to know. Editing requires being an organization administrator. Secrets always go as a vault reference, <<vault:…>>; never in clear text.

6. Test with a device

This is the best way to understand a service. Pick a device from the menu, grouped by site, and you get three columns side by side:

ColumnWhat it shows
1. ValuesThe device's values for this service and which scopes they come from. Each scope is a button that opens its declaration for editing.
2. TemplateThe service's Jinja template.
3. What it generatesThe configuration it generates today on that device.

The template, the JSON and the XML are colored as in VS Code. In column 3, whatever comes from the device's parameters is highlighted; hover over it to see which parameter it comes from. Anything not highlighted is fixed in the template.

Test these values

In column 1 you can change the values and click Test these values. Oktavia renders with the same engine used by audits and shows you the difference. Nothing is saved. Use it to answer "what would happen if…?" before touching intent.

If the test says "nothing changes". Some values come from the device inventory, for example ospf_config.router_id, and win over the service's values. If you change one of those in the service, the configuration doesn't move. Check the device inventory.

7. Explain this service

Click ✦ Explain this service and Argos, with local AI or with Claude, explains:

  • what the service does;
  • each parameter;
  • what it generates on the device you picked;
  • tips for using it well.

Argos receives the template, the masked values and the generated output. It never receives secrets or the device's full running configuration.

8. IOS XR: no Jinja, XML instead

On IOS XR there is no Jinja template. The NETCONF lane builds the YANG XML from the same values. The service page works the same way, with these differences:

  • Column 2: explains how the NETCONF lane builds the configuration.
  • Column 3: shows the XML for the chosen device. The device's values are highlighted here too, so you can tell what comes from variables from what is fixed in the lane.
  • See what changes and Test these values compare today's NETCONF plan with the plan for your change, exactly as the Digital Twin would push it, with commit confirmed.

This applies to core services and to customer services. There is a recipe in section 14.

9. Extending a service

When the base template doesn't include what you need, you extend it. There are two ways in:

  • Advanced options: tested extensions from the Oktavia catalog, enabled with one click. For example, in OSPF: timers, BFD and area types; in BGP: per-neighbor timers, address-family and aggregates; on interfaces: bandwidth.
  • Extend here, on the row of the scope where you want the values, or ＋ Extend this service.

Extend here, in three steps

  1. What do you want to add? Pick it from the Oktavia catalog with one click, or describe it and generate it with Argos (local AI or Claude).
  2. Parameters. What you fill in, and its network test.
  3. Advanced template. Already resolved and folded, in case you want to adjust it.

The extension's values stay in the intent (service_vars), in the same scope where you clicked Extend here. They reach the devices through the cycle: audit → compliance → Digital Twin → you approve → verification.

10. The gate before publishing

Before an extension is published, a deterministic gate checks it. It is not an AI opinion: these are fixed rules.

RuleWhat it checks
Blocked commandsThe template carries no forbidden commands.
No literal secretsNot even type 7. Secrets go as <<vault:…>>.
Clean removalRemoving the extension only uses no or default.
CollateralIf the extension changes lines that belong to another service, it is not published.

Then click Validate on these devices: Oktavia renders the extension on real devices without touching the network. It is published only once validated.

11. An extension's network tests

An extension doesn't end at the configuration: it also says how to check that it works. There are two kinds of test.

State tests

They check that something is up: BGP or OSPF neighbors, interfaces, BFD, IS-IS, routes. They are derived from the parameters. For example, neighbors[].address yields the list of neighbors that must be established.

Value tests

They compare what is seen on the network with what you declared. It is not enough for the neighbor to be up: it also has to have the right value.

  • BGP timers negotiated with each neighbor.
  • OSPF hello and dead per interface.
  • SNMPv3 users: group and protocols, without keys.

The catalog extensions bgp_timers and ospf_timers already ship with their value test. When you audit you will see, for example, "BGP · timers negotiated with the neighbor". Value tests exist today on IOS and IOS XE.

12. Custom services

When what you need doesn't extend an existing service, create a new one in Services → Custom services.

  1. Describe the service or paste a sample configuration.
  2. Argos proposes the template, the fields and a sample of values.
  3. The same gate from section 10 decides whether it can be published.

From there you can also open View template for any service, to read it without editing it.

13. With Argos: Services by domain

If you'd rather ask in your own words, open Argos → Configure → Services by domain. What used to be the Configurator assistant now lives here.

  1. Pick the domain and the service. Only those for the platforms in your network appear.
  2. Say which values you want and where, for example timers 10 30 en los wan_router. You can also bring them in from a device backup.
  3. Argos proposes the change. Click 🔍 What changes on the devices to see the desired configuration per device before saving.
  4. If it is what you wanted, click Apply and close the cycle. You still approve the change in the Digital Twin.

14. Recipes

BGP · Timers 10/30 on one neighbor

You want to detect a provider failure sooner. The BGP template has no per-neighbor timers; the catalog extension bgp_timers does.

  1. In Services → WAN, open the BGP service.
  2. In Declared values, find the router's scope, usually by_device, and click Extend here.
  3. Pick BGP · per-neighbor timers from the catalog and fill in the parameters: 
    {
  "neighbors": [
    { "address": "198.51.100.1", "keepalive": 10, "hold": 30 }
  ]
}
  4. Click See what changes. A single new line should appear, on that device: 
    r1
  router bgp 65001
+  neighbor 198.51.100.1 timers 10 30
  5. Save and close the cycle. Approve the change in the Digital Twin.
  6. After verification, review the device's compliance: the value test BGP · timers negotiated with the neighbor appears. The neighbor negotiates the lower hold: if the other side has a lower one, that is what you will see.

Interfaces · Add bandwidth

The interfaces template has no bandwidth, and you need it for OSPF or EIGRP cost and for a percentage-based QoS. bandwidth does not change the real link speed.

  1. Open the router's interfaces service and, in Advanced options, enable Interfaces · bandwidth (interface_bandwidth).
  2. Fill in one entry per interface, in kbps: 
    {
  "interfaces": [
    { "name": "GigabitEthernet4", "bandwidth_kbps": 50000 }
  ]
}
  3. In Test with a device, pick the router and check column 3. What is highlighted comes from your parameters: 
    interface GigabitEthernet4
 bandwidth 50000
!
  4. Save and close the cycle. The extension's state test checks that the interface stays up.

A new service with Argos from a sample config

You want an IP SLA probe toward the provider gateway on every branch router, and there is no service for it.

  1. Open Services → Custom services and paste the configuration you already use on a device: 
    ip sla 10
 icmp-echo 198.51.100.1 source-interface GigabitEthernet2
 frequency 30
ip sla schedule 10 life forever start-time now
  2. Argos proposes the template, the fields (for example, probe number, target, source interface and frequency) and a sample of values. Check that what varies is a field and what is fixed stays fixed.
  3. Click Validate on these devices with two or three routers. If the gate rejects something, fix it before moving on.
  4. Publish, declare the values in the right scope, for example by_role, and close the cycle.

IOS XR · A new BGP route reflector client

You are adding a new PE as a route reflector client and want to see the XML that changes before saving.

  1. In Services → Transport, open the core BGP service (xr_bgp).
  2. In Test with a device, pick the route reflector. Column 3 shows its XML, with the values highlighted.
  3. In column 1, add the new PE's loopback to clients. Remember: a list is rewritten whole. 
    {
  "asn": 65000,
  "route_reflector": true,
  "clients": ["192.0.2.11", "192.0.2.12", "192.0.2.13"]
}
  4. Click Test these values. Oktavia compares today's NETCONF plan with the plan for your change and shows the new neighbor: 
    + <neighbor>
+   <neighbor-address>192.0.2.13</neighbor-address>
+   <remote-as>65000</remote-as>
+   <update-source>Loopback0</update-source>
+   <address-families>
+     <address-family>
+       <af-name>vpnv4-unicast</af-name>
+       <route-reflector-client/>
+     </address-family>
+   </address-families>
+ </neighbor>
  5. If it is as expected, edit the declaration with Edit values, check See what changes and save.
  6. The core changes as a single transaction with commit confirmed: if you don't confirm, the devices roll back on their own.

15. Good practices

  • Test before saving. "Test these values" saves nothing: use it freely.
  • Read "See what changes" device by device. If a device you didn't expect appears, check the scope.
  • Prefer the catalog. A catalog extension is already tested and ships with its network test.
  • Extend, don't copy. The base template is not edited; your work lives in the extension and the values.
  • Declare at the most general scope possible. Same as with intent: by_device only for what belongs to the device.
  • Give every extension its test. A service with "no tests" won't warn you when it stops working.
  • No secrets in clear text. Everything through the vault, with <<vault:…>>.
  • Verify with compliance. A change ends when the audit confirms it.
