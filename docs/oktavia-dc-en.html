1. Product summary

Oktavia DC is the Oktavia installation for the data center: it builds and runs the Cisco Nexus VXLAN EVPN fabric —underlay, BGP EVPN, VTEPs and vPC— and orchestrates, on the same platform, each application's services. It is not a separate product: it is the same Oktavia Pro loop —audit, compare with the intent, propose in the Digital Twin, approve, apply, verify and audit again— with a service catalog and screens of its own for the data center.

It is lab-tested with Cisco Nexus 9000v (NX-OS 10.5) in a spine-leaf fabric with vPC, and a Cisco IOS XE exit router.

What sets Oktavia DC apart: an application is declared once —VRF, network, port or external exit— and Oktavia generates the part for each leaf, border and spine; every Nexus in the change enters a single transaction with a checkpoint and automatic rollback; only the missing lines are sent; and each service has its own page with its per-device components, its real state and the data of the application that uses it. No change reaches the network without a person approving and confirming it.

2. The approach

Intent per service, not per device

A new network in a fabric touches the VLAN, the VNI, the anycast SVI, EVPN and the NVE on every leaf, the VRF on every VTEP and the server port on the vPC pair. In Oktavia DC that is a single declaration: Oktavia knows which devices get each line and derives the repetitive parts, such as each VRF's RD and RTs.

Model-driven on NX-OS

Nexus switches are managed over NX-API (JSON-RPC over HTTPS), with each device's certificate fingerprint accepted by a person. No screen scraping.

Only what is missing

The change plan is compared with each Nexus running config and only the new lines are sent. What is already right is not sent again, and a small change stays small.

Deterministic first

Configuration generation, the change plan, compliance and fabric state are computed without AI, with reproducible results. AI —local, on your server, or Claude— is used to explain, diagnose and draft, and every action says before you press it whether it uses AI.

4. The fabric and the service catalog

The fabric baseline

The baseline comes from the fabric plan: OSPF underlay between spines and leafs, iBGP EVPN with the spines as route reflectors, each VTEP's NVE interface, and the vPC domain with its peer-link and keepalive. It is declared, audited and corrected with the same loop as the services.

Each application's services

ServiceWhat it generatesWhere
Tenant VRFThe VRF with its L3VNI, automatic RD and RTs, and its networks advertised as EVPN type 5Every VTEP
Server networkVLAN, L2VNI with BGP ingress replication and anycast gateway: the same IP and MAC on every leafThe network's leafs
Server portSingle access or vPC with LACP on the leaf pair, as a spanning-tree edgeLeaf or vPC pair
External exitBorder interface in the VRF and eBGP with the WAN router: the default route enters the fabric and the application's networks go outBorder leaf and WAN router

On top of these come the NX-OS platform services: SNMP and per-role hardening, also as intent.

5. Orchestrated services and each service's page

The orchestrated services table shows every VRF, network, port and external exit with its site, devices, values and state (up, partial, down, not applied), with filters, search and CSV export. It has the same structure as Oktavia SP's Customer services, without the customer: each row is a service.

  • Service page. Its values, its path through each Nexus —declared versus seen— and the Twin changes that touched it, with a shortcut to diagnose it with Argos.
  • Components. A composite service breaks down into its parts (underlay, BGP, VTEP, vPC…) with their per-device parameters and what is missing according to the last audit.
  • Application data. Custom per-service fields to document which applications and which traffic run through each network: application, owner, criticality, environment, expected traffic and CRQ. Added without programming, and included in search and in the CSV.

6. Adding an application: form, workflow or Argos

A new service comes in by three paths, and all three end in the same Digital Twin change:

  • Form. «Fabric services» asks for the VRF, network, port or exit data and checks that it does not clash with what already exists.
  • Operations workflow. End-to-end application onboarding —VRF, networks, ports and exit— with the workflow simulated before anything is written.
  • Argos. The same workflow from the chat, with the change and its diff in view before approval.

7. The closed loop: one transaction across every Nexus

  1. Proposal. The Digital Twin builds the plan for each Nexus in the change and shows the per-device diff.
  2. Approval. A person reviews and approves.
  3. Checkpoint. Each Nexus saves a checkpoint before anything is touched.
  4. Configuration. Only the missing lines are sent.
  5. Verification. OSPF, EVPN sessions, VNIs and vPC. If a device rejects a line or the fabric does not converge, all of them roll back to their checkpoint on their own.
  6. Confirmation. The change waits for confirmation; once confirmed, the configuration is saved to startup and the checkpoint is removed. Without confirmation, the fabric goes back to the checkpoint.
  7. Audit. Compliance compares the intent with the running config again to prove the finding closed.

Long changes run in the background and the screen follows their progress; a failed change can be retried from Argos.

8. Compliance and fabric state

  • Configuration. Each service is compared with the running config block by block, with the exact missing or extra line.
  • State. State rules check OSPF adjacencies, BGP EVPN sessions, VNIs up and the vPC pair with its keepalive.
  • Software. Each device's NX-OS version against the standard for its model.

9. Visibility: per-VRF routing, topology and connectivity

  • Per-VRF routing. Each Nexus routing tables by VRF, with the VXLAN hop to the remote VTEP and the exit through the border; routing analysis and IP Intelligence follow an application's real path.
  • ARP and MAC. Where each server is: its IP, MAC, leaf and port.
  • Topology. The fabric with the site AS shown once, the iBGP sessions and the OSPF adjacencies.
  • Connectivity test. Ping from the Nexus itself over NX-API, inside the right VRF.

10. Security, telemetry and FinOps

  • NX-OS hardening. The per-role hardening standard is declared as intent, audited and corrected with the same loop.
  • Vulnerabilities. The NVD and CISA KEV CVEs that apply to each device's NX-OS version: what to address first.
  • Telemetry. SNMP on the Nexus switches enabled as a service; the community lives in the vault, never in the intent.
  • FinOps. Fabric cost and the operational savings from automation, per site and domain.

11. Argos and local AI in the data center

Argos diagnoses the fabric and each application, runs onboarding workflows from the chat and explains changes. Local AI answers from the VXLAN, EVPN and vPC documentation and your team's runbooks, without sending the running config to the cloud; AI only receives bounded summaries per device or site, never secrets. Every action says before you press it whether it uses AI, and AI never decides whether something complies.

12. Deployment and security

  • One codebase. Oktavia DC is the same platform as Oktavia Pro and Oktavia SP; the data center mode comes from the tenant.
  • Installation. Containers on a Linux server with Docker, on your premises or in your private cloud. Sizing is in the Oktavia Pro technical sheet.
  • Platform security. Credentials encrypted in the vault, per-tenant data separation, IP access allowlist, sign-in through your identity provider with a second factor. Each Nexus NX-API certificate fingerprint is accepted by a person.
  • Test network. Changes are rehearsed in Cisco Modeling Labs before touching production.
